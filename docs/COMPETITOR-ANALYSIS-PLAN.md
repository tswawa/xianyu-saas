# 竞品资料分析与一体化优化计划

更新日期：2026-08-17

本文根据仓库内 `蒸馏/` 的 14 张竞品截图，并结合当前代码结构整理。截图中的功能文案是市场需求信号，不视为对竞品真实能力的验证。计划遵循一个决定：前端只保留少量、一体化的经营入口，复杂度放在后端状态机、账号隔离、任务恢复和履约安全上。

## 结论先行

产品不需要复制竞品的几十个开关。第一阶段只做一条稳定闭环：

```text
连接一个闲鱼账号 -> 自动整理商品 -> 选择简单策略 -> 自动回复/履约 -> 异常进入人工处理
```

后端必须保证四件事：

1. 任何事件都带有明确的 `account_id`，不能串店铺。
2. 同一事件重放不会重复回复、重复扣库存或重复发货。
3. API、worker 或网络重启后，任务能继续、重试或进入人工审核，不能静默丢失。
4. AI 只能提出候选回复，发送和履约必须经过服务端规则与订单证明闸门。

### 成熟商品 UI 的可复用结构

蒸馏中的成熟商品详情页（移动端）反复使用同一条成交路径：首屏先给出商品标题、价格/优惠、服务量或信任信号；随后用短段落和要点说明解决什么问题、适合谁、如何使用；中段放真实功能截图或案例；底部固定购买/咨询动作。桌面后台则把账号、会话、商品和订单上下文分栏，减少来回跳转。

本项目只吸收结构，不复制竞品图片或宣传承诺：会员页采用“价值说明 -> 免费/会员权益 -> 套餐价格 -> 支付状态”的单页路径，突出 `¥1` 日卡作为低门槛入口；免费用户只展示日卡、周卡，进入会员模式后再展示月卡、年卡；支付链接未配置时明确保持不可用。复杂的套餐生效、权限校验和支付回调仍由后端负责，前端不增加多余开关。

### 2. 详情页反复出现的需求信号

`0AB6...jpg`、`13425...jpg`、`3FF8...jpg`、`67A7...jpg`、`6BAB...jpg`、`ABA2...jpg`、`F136...jpg`、`FADD...jpg`、`FCC5...jpg` 反复宣传以下能力：

- 多账号同时在线、账号启停和重连。
- 关键词回复、商品专属回复、AI 回复和提示词/商品资料结合。
- 固定文字、卡密、网盘、第三方 API 等多种履约方式。
- 自动重试、防重复发送、订单状态监控和异常提醒。
- 商品批量导入/导出、批量设置和商品级规则。
- 会话历史、未读提醒、统计和运行日志。

这些内容可以归并为五个后端域：`账号`、`消息`、`策略`、`履约`、`运营状态`。不应按竞品宣传句子逐项复制成五十个前端功能。

### 3. 不能直接照搬的宣传内容

- “全平台通用”“永久免费”“无需任何配置”“自动改价/擦亮/好评”等，截图没有提供安全、合规或稳定性的证据。
- 多平台接入会显著扩大登录、签名、订单证明和风控边界，当前只聚焦闲鱼。
- 自动评价、自动改价、批量搬运和图片生成属于高风险动作，暂不进入核心闭环。
- “本地部署、同 IP、手机挂机”是竞品卖点，不等于本项目必须做桌面端或手机端。当前单机 FastAPI + SQLite + worker 更简单可控。

## 二、当前项目对照

### 已具备的基础

- 已有官方二维码登录、Cookie 验证、商品快照和免费关键词/资料发送流程。
- 已有 `shop_accounts`、按账号目录隔离、持久 jobs/leases、worker 运行状态和 API 重启恢复边界。
- 已有 worker 侧消息幂等、会话库、订单核验、库存预占、重试和人工审核状态机。
- 已有会员 AI 代理、会话/订单查询和 attention 摘要接口。
- 前端已经是少入口工作台，免费用户不会看到会员工作流。

### 与资料相比的真实缺口

| 缺口 | 当前影响 | 优先级 |
| --- | --- | --- |
| 通用后台 job consumer 尚未独立运行 | 店铺同步虽然有持久任务边界，但仍可能占用 API 请求；API 重启后的通用任务不能自行消费 | P0 |
| 统一事件模型尚未覆盖所有控制面动作 | 消息、同步、履约、人工控制的审计和重放边界分散 | P0 |

| 会话接口缺少搜索、未读、人工接管和状态聚合 | 能查看记录，但还不是竞品截图中的经营收件箱 | P1 |

## 三、目标后端结构

### 1. 统一上下文

每个请求、任务、事件、文件和 worker 环境都解析为：

```text
user_id -> account_id -> product_id(可选) -> chat_id(可选) -> event_id
```

服务端从会话和账号上下文得到作用域，不能信任浏览器传来的目录、商品标题或买家文字来授权操作。

### 2. 统一事件链

```text
平台事件
  -> 账号校验与规范化
  -> 幂等去重
  -> 会话/商品绑定
  -> 账号默认策略 + 商品覆盖 + 会话人工接管
  -> 确定性规则
  -> AI 候选（可选）
  -> 发送/履约安全闸门
  -> 平台回执
  -> 审计、统计、attention
```

每个事件至少保存 `event_id`、`account_id`、来源、策略版本、状态、尝试次数、最后错误码和下一次可执行时间。原始 Cookie、买家正文和库存内容不进入控制面日志或公开接口。

### 3. 状态机边界

- 任务：`queued -> running -> completed / retry / dead_letter`。
- 消息：`received -> deduplicated -> pending_reply -> sent / no_reply / manual`。
- 履约：`verified -> reserved -> sending -> delivered / retry / manual_review`。
- 账号：`unconfigured -> verifying -> ready -> degraded / expired`。

任何状态转换都必须带租约所有者或事件键；超时只允许重试同一个事件/预留，不允许重新生成另一份库存或另一条回复。

## 四、分阶段实施顺序

### P0：先把后端闭环做稳

1. **独立 job consumer**
   - 只消费无明文凭据的持久任务；从 `jobs` 表领取租约、续租、指数退避，超过上限进入 dead letter。
   - `shop_sync` 的替换 Cookie 不写进任务 payload；需要恢复的刷新任务从账号安全目录读取已验证 Cookie。
   - API 只负责提交和查询摘要，避免长时间同步占住请求线程。
   - 验收：杀掉 API/consumer 后任务可恢复；同一幂等键只执行一次；失败不会覆盖旧快照。

2. **统一事件外壳**
   - 为消息、同步、人工接管、履约回执统一生成事件键和审计状态。
   - 将 worker 现有的幂等/重试事实源保留为履约权威，不复制一套库存数据库。
   - 验收：同一平台事件重放、网络超时、进程退出都能得到确定终态。

3. **策略版本化**
   - 后端存储“账号默认策略、商品覆盖、会话人工接管”和策略版本。
   - 前端只暴露三个预设：保守、标准、积极，以及一个总开关；不暴露几十个底层参数。
   - 每条回复记录命中的策略版本，改规则不会改写历史。

### P1：补齐经营闭环

4. **统一收件箱后端**
   - 扩展现有会话接口，增加账号、未读、最后消息时间、商品绑定、处理状态和安全分页。
   - 搜索只在受控字段上执行；`chat_id`、`account_id` 始终由服务端校验。
   - [第一步已完成] 人工接管/恢复使用账号私有状态；人工回复 outbox 在发送前再次检查接管状态，发送期间续租，过期 owner 不可回写，以稳定 UUID 有界重试并回写平台协议 ACK。异常进入账号 attention，人工回复不计自动回复统计；买家已读回执、平台 UUID 去重和跨设备实时推送仍待实现或真实验收。

5. **履约适配器**
   - 统一 `text`、`redeem`、`pan`、`api` 四类适配器的校验、预占、发送、回执、补偿和人工审核接口。
   - 商品绑定只接受已验证快照中的商品 ID；买家文字、商品标题和截图不能授权发货。
   - 每种适配器先做离线合同，再由用户安排受控真实验收。

6. **商品与批量操作服务（资料批量第一步已完成）**
   - 已完成当前账号商品的资料批量预览、局部原子提交和批量暂停；未接入闲鱼平台发布、上架或改价。
   - 后端支持商品版本、上下架变化、SKU/规格映射、批量启停和批量导入校验。
   - 导入采用预览 -> 校验 -> 一次提交；错误行不影响已生效配置。
   - 前端只保留“选择商品 + 选择策略/资料”的简单流程，不做复杂表格编辑器。

7. **运营状态和统计**
   - 从事件状态生成有限聚合：今日消息数、自动回复数、人工接管数、履约成功/失败数、平均处理耗时。
   - attention 只展示需要动作的摘要：需重新登录、同步失败、worker 停止、履约待审核。
   - 统计为可重建的派生数据，不作为履约事实源。

### P2：验证后再加

- 快捷短语和模板：先做后端版本/权限/账号作用域，再决定是否显示一个“常用回复”抽屉。
- 团队成员和角色：只有出现多人协作需求后再加入，不提前复制竞品的多用户管理页。
- 商品变更通知、定时同步和导入导出历史。

## 五、前端保持一体化的落法

工作台最多保留以下入口：

1. **工作台**：当前账号、连接状态、需要处理的 attention、今日摘要。
2. **店铺与商品**：账号切换/连接、商品卡片、同步状态。
3. **自动化**：三个策略预设、商品资料绑定、开启/暂停。
4. **对话与订单**：会员可见的统一收件箱，右侧显示商品/订单上下文。
5. **会员服务**：套餐和支付入口。

账号管理采用顶部账号切换器或一个抽屉，不单独复制复杂的竞品后台导航。系统日志、任务租约、重试次数、死信和适配器细节只进入后端管理/运维接口，不进入普通店主界面。

## 六、验证与交付闸门

### 离线合同

- 双账号同键隔离：商品、会话、订单、规则、库存和任务互不覆盖。
- 重放与恢复：事件幂等、租约续期/过期 owner、ACK 落库前崩溃、指数重试、死信和 API/worker 重启。
- 权限与安全：免费/会员、账号停用、路径/symlink、防明文凭据、AI 作用域。
- UI：只验证入口数量、账号上下文、移动端布局和错误状态，不把宣传截图当作验收标准。

### 受控真实验收

按“一个测试账号、一个测试商品、一个测试订单”顺序进行：扫码/安全验证 -> 商品同步 -> 规则回复 -> AI 候选 -> 订单核验 -> 测试履约 -> 失败重试 -> 人工接管。真实买家、库存、订单正文和生产 Cookie 不进入自动化测试。

## 七、暂不做的内容

- 淘宝/拼多多等多平台适配。
- 独立桌面端、移动 App、手机挂机和浏览器自动化扩张。
- 自动改价、擦亮、评价、批量搬运、图片生成和高频营销动作。
- 公开插件市场、开放 API、复杂 CRM、拖拽式流程编排。
- 把竞品详情页中的“永久免费、全自动、零配置”作为产品承诺。

## 完成标准

不是“页面看起来像竞品”，而是：一个普通店主只需选择账号、连接店铺、选一个策略即可运行；后端能证明每条消息和每次履约属于哪个账号、为何执行、失败后去了哪里，并且重启后不会重复发送或串店。
