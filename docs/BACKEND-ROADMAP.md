# 后端优先路线

本项目的产品约束是：前端一体化、少入口；复杂度放在服务端的账号隔离、任务状态和异常恢复。本文记录竞品截图与当前代码审阅后的实施边界。

竞品资料逐项分析和分阶段实施计划见：[竞品资料分析与一体化优化计划](COMPETITOR-ANALYSIS-PLAN.md)。

## 当前已经落地

- `backend/db.py` 增加 `shop_accounts`。旧租户启动时自动拥有一个 `default` 账号，原有按用户存放的运行文件仍兼容。
- `jobs` 提供有界 payload、幂等键、租约、续租、重试和死信状态；同一用户的不同账号可以使用相同业务键而不冲突。
- `worker_runtimes` 保存期望运行状态、模式、PID、代次和心跳。启停接口会先后更新进程与持久状态，API 重启时会尝试认领仍要求运行的 worker。
- API 重启恢复已加入 PID 认领边界：只接受命令行、工作目录和租户目录均匹配的存活进程；免费 `rules` worker 可安全认领，会员 `rules_ai` worker 因令牌只存在旧 API 内存而会先验证并替换，不复用失效令牌。
- 恢复过程使用账号级持久控制租约；发现存活但身份不匹配的 PID 时进入 `degraded`，不自动杀进程或再启动副本。
- `/api/bot/accounts` 只返回账号健康元数据；不返回 Cookie、Token、订单正文或库存内容。
- 商品快照、Cookie、规则、履约配置、会话库和履约库已按账号目录隔离；账号选择由服务端校验的 `X-Shop-Account` 作用域承载。
- 同步租约键包含 `user_id + account_id`，attention、任务幂等键和 worker 环境路径均有双账号离线合同覆盖。
- 用户退出时会清理该用户所有账号的二维码登录会话和连接助手凭据。
- 托管 AI worker 的内部令牌和 `X-Shop-Account` 头按账号绑定；loopback 代理会复核账号存在、启用状态和会员权限后才转发，且不会把作用域头传给上游。
- `worker/delivery_store.py` 仍是履约事实源，没有被新的控制面表替代。
- `backend/job_consumer.py` 已提供独立的 `shop_sync` 刷新消费者：只读取账号目录中已保存的 Cookie，任务载荷只保留指纹，支持租约续期、重试和死信；`Prefer: respond-async` 的刷新请求会返回可轮询的任务摘要。扫码完成、手动 Cookie 替换仍保留同步路径。
- 前端顶部已提供账号切换抽屉：新增账号只填写备注，服务端生成内部标识；当前账号按用户名保存浏览器偏好（只保存标识，不保存 Cookie/Token），切换后重新加载商品、规则、会话、订单和 worker 状态。
- 自动化设置已增加账号级“保守 / 标准 / 积极”策略预设和总开关；关闭总开关会持久化并停止当前账号 worker，重新开启前必须由用户明确启动。
- UI 合同已覆盖账号创建、切换、作用域请求和桌面/移动端抽屉布局；这证明浏览器交互和隔离头发送，不等于真实闲鱼多账号验收。
- 工作台已接入当前账号的 attention 摘要；会员账号额外显示消息、订单、履约和待处理计数。统计是可重建展示数据，不替代履约事实源。
- `/api/bot/analytics` 已提供会员账号范围内的 1/7/30 天有限聚合：消息、自动回复、人工接管、履约成功/待处理和未读数；人工回复不计入自动回复，接口不返回消息/订单正文、库存、凭据或业务标识，工作台只增加一行今日数据。
- 商品批量资料第一步已接入：预览凭证绑定当前账号、商品快照、配置和请求，提交只原子更新所选商品；前端复用商品/自动化入口，不增加复杂表格或独立导航。这是本地自动履约配置，不是闲鱼平台批量发布。
- 人工回复发送第一步已接入：旧草稿不会自动发送，新回复在人工接管状态下写入账号私有 outbox；worker 在发送期间续租，过期 owner 不能回写 ACK/失败，以同一消息 UUID 做最多 10 次有界重试。平台协议 ACK 后才显示“闲鱼已接收”，异常会进入当前账号 attention；人工回复不计入自动回复统计。最近 2000 条确认记录保留完整 outbox，较旧记录压缩为最多 50000 条无正文幂等 tombstone。该链路是至少一次投递加稳定 UUID，平台是否按 UUID 去重仍未真实验证，ACK 也不等于买家已读或最终送达。

## P0：先完成可靠性

1. [已完成基础] 将店铺同步的冷却、全局闸门和熔断从进程内变量迁移到持久租约；同步请求变成可恢复的 `shop_sync` job。
2. [已完成基础] 为每个账号建立运行目录映射。旧 `default` 继续使用原目录，新账号使用独立目录；商品快照、会话库、履约库、规则和连接状态均按账号路径读取，兼容字段不会把新账号回退到旧账号。
3. [已完成第一阶段] 增加独立 `shop_sync` job consumer：租约过期自动回收、租约续期、指数退避，超过上限进入死信；API 可只提交和查询刷新摘要。其他任务类型仍需各自消费者。
4. [已完成基础] 增加统一 `attention` 读取接口，只返回“需要重新登录、同步失败、worker 停止、履约待审核”等摘要，并按当前账号过滤。

P0 验收：重启 API 不重复启动 worker（离线恢复合同已覆盖）；同一事件重放只产生一个任务；两个账号使用相同商品/订单键不串数据（双账号隔离合同已覆盖）；进程在发送中退出后只能重试同一预留或进入人工审核。

## P1：核心经营闭环

- 消息规范化链：平台事件 -> 幂等去重 -> 会话/商品绑定 -> 确定性规则 -> 安全检查 -> AI 候选 -> 服务端发送闸门 -> 审计。
- [已完成第一步] 策略采用账号级默认设置，前端只显示保守/标准/积极三个预设和一个启停入口；商品覆盖、会话人工接管和事件策略版本仍待统一事件外壳完成。
- 履约适配器统一文字资料、卡密、网盘和第三方 API 的核验、预占、发送、确认、补偿接口；继续复用 `DeliveryStore` 的库存和订单证明校验。
- [发送第一步已完成] 会话、订单、商品查询已在 API 层按当前账号强制作用域；统一收件箱具备搜索、未读游标/筛选、会话状态、人工接管/恢复和持久人工回复 outbox。接管复用账号独立 `delivery_state.db` 的 `manual_modes`；发送租约续期、过期 owner 拒写、稳定 UUID 恢复、平台协议 ACK 回写和账号切换迟到响应隔离均有离线合同。买家已读回执、平台 UUID 去重、跨设备实时推送和完整事件级审计仍待实现或真实验收。
- [第一步已完成] 商品页支持当前账号已验证商品的批量资料预览/提交和批量暂停；preview token 绑定商品快照与配置，提交只改选中商品并保留其他资料、兑换码和网盘映射，响应不回显资料正文。批量导入/导出、商品变更检测和定时同步仍待实现。

## P2：验证后再加

- [已完成第一步] 工作台 attention、会员经营计数、统一收件箱摘要和 1/7/30 天有限运营聚合已接入；已解决的人工审核不会继续计入待处理，统计仍是可重建派生数据。回复率、平均处理耗时、关键词提取和通知仍待统一事件模型完善。
- 批量导入/导出策略、商品变更检测和定时同步。
- 自动评价、自动改价、高频擦亮和商品图片生成等高风险或宣传型能力暂不接入。

## 不引入

当前不引入 Redis、Kafka、Celery、微服务、桌面端或移动端。单机 FastAPI + SQLite/WAL + supervisor + 按账号 worker 足以覆盖本阶段容量，也更容易备份和恢复。

## 验证边界

离线合同通过只证明状态机和权限边界；真实扫码、安全验证、商品同步、平台消息发送和真实订单履约仍需受控验收，不能用测试结果替代。
