# 后端路线图

本文面向希望了解服务端边界的贡献者。路线图描述方向，不替代接口文档或实际发布记录。

## 已建立的基础

- FastAPI 控制面按用户和店铺账号隔离身份、配置、商品、会话、订单和 Worker 运行态。
- SQLite 持久化任务、租约、幂等键、重试和死信状态；API 重启后可恢复需要继续运行的任务。
- 店铺同步由独立任务消费者处理，任务载荷不保存平台 Cookie 原文。
- Worker 生命周期、账号作用域和进程身份由控制面统一管理。
- AI 回复经过统一内容引擎，实际发送前再次核对自动化状态、AI 状态和精确配置版本。
- 统一收件箱支持会话搜索、未读状态、人工接管和持久人工回复 outbox。
- 人工回复一次提交支持最多 8 张图片和文字；按图片顺序逐段发送、逐段等待协议 ACK，失败只恢复未确认部分。
- 履约事实仍由 Worker 的订单核验、库存预留和状态机负责，AI 不参与履约授权。
- 运营摘要、待办和安全管理接口按当前账号或平台管理员权限返回有限信息。

## P0：可靠性

1. 继续完善跨进程租约、进程退出回收和恢复幂等，确保停止、重启和网络超时不会生成重复消息或重复扣库存。
2. 统一消息、同步、人工接管和履约回执的事件外壳，保留 Worker 履约数据作为事实源。
3. 补充真实平台状态的可观测性，同时确保日志和错误信息不泄露凭据或业务正文。

## P1：经营闭环

1. 完善统一收件箱的分页、实时更新、跨设备状态和买家回执边界。
2. 完善商品变更检测、定时同步、批量导入/导出和配置版本提示。
3. 将统计和 attention 继续作为可重建派生数据，不替代订单和履约事实。
4. 优化容器、systemd、签名更新和回滚合同，明确两种部署方式的边界。

## P2：验证后再做

- 更多受控 provider 和平台错误恢复；
- 更细的通知、审计和运营指标；
- 依赖许可证、SBOM、可复现构建和更严格的供应链验证；
- 只有在账号隔离和权限模型足够稳定后，再评估团队协作能力。

## 不引入

当前阶段不引入 Redis、Kafka、Celery、复杂微服务、独立桌面端或移动 App。单机 FastAPI + SQLite/WAL + 任务消费者 + 按账号 Worker 更适合当前容量和恢复模型。

## 验证边界

离线合同只能证明代码路径、权限和状态机边界。真实扫码、安全验证、平台消息发送、第三方模型质量、商品同步、订单履约和生产部署需要受控环境单独验收。
