# AI 客服内容驱动需求文档

更新日期：2026-08-28

## 1. 目标

AI 客服面向非技术店主。店主只需要填写真实的店铺与商品说明，系统根据以下资料动态回答买家的当前问题：

1. 平台安全与履约边界。
2. 当前店铺保存生效的自然语言客服内容。
3. 当前商品实时标题、描述、价格、库存、SKU 和状态。
4. 当前商品可选的自然语言补充内容。
5. 当前 `chat_id` 的有界对话历史。
6. 当前买家消息。

JSON 只作为账号私有文件和 HTTP 协议的内部实现。普通页面不得要求店主编辑 JSON、理解字段结构、批准结构化配置或维护提示词。

此前“单商品结构化知识库 + 草稿 + 发布”的产品模型已经被本文件替代。历史 v1 数据只做兼容迁移，不得继续决定新页面交互。

## 2. 核心原则

### 2.1 真正回答当前问题

- 固定关键词规则命中时原样发送，模型调用次数为零。
- 未命中固定规则且 AI 可用时，每一条有实质文字的买家消息都必须进入统一回复引擎。
- `rules_ai` 首次咨询不得被欢迎语或 `first_reply` 覆盖。
- 模型必须先回答当前问题，只引用相关资料，不复述整份店铺或商品内容。
- 连续追问必须结合当前会话历史，不得把每一轮都当成新会话。
- 没有足够事实时应指出具体缺失项或转人工，不能发送与问题无关的固定寒暄。

### 2.2 内容优先，结构隐藏

- 店铺内容以自然语言为主，可辅以人格、语气、称呼、回复长短和表情等简单选择。
- 商品内容以自然语言补充说明为主，系统同步的实时商品事实只读展示。
- FAQ、规格、售后和交付说明可以写在同一份内容中，不要求店主拆成固定 JSON 字段。
- 模型整理功能只生成自然语言建议预览；店主确认采用后仍需单独保存。
- 空白、纯标点、默认占位或所有字段为空的旧对象都不算有效内容。

### 2.3 唯一生成链路

沙盘测试与真实自动回复必须调用同一个控制面回复引擎，并使用相同的：

- 配置读取；
- 上下文分层；
- 字符预算与压缩规则；
- provider adapter；
- 输出解析；
- 安全检查；
- 重复回复判断；
- 错误码语义。

worker 不再自行编译店铺/商品知识，也不再运行价格、技术、默认等多 Agent 分类链。

### 2.4 AI 不授权业务副作用

AI 只能生成客服文本或返回 `handoff/no_reply` 决策。AI 输出不得触发：

- 试用码、兑换码、网盘资料或教程资源发送；
- 订单付款状态变化；
- 自动发货或履约状态变化；
- 人工审核通过；
- 任何由 `-`、`[TRIAL]`、`[TUTORIAL]` 等魔法字符串代表的内部动作。

自动履约仍只依赖平台订单证明，并核验订单、商品、买家、卖家、状态和数量。

## 3. 模型连接

首批支持五种受限格式：

- `openai_chat_completions`
- `openai_responses`
- `anthropic_messages`
- `google_gemini`
- `ollama_chat`

要求：

- 用户自行填写 provider、Base URL、模型名和所需 API Key；系统不提供默认上游或共享调用额度。
- API Key 只在服务端使用主密钥加密保存，不回显给前端、worker、日志或公开 API。
- worker 只持有绑定 `user_id + shop_account_id + account_key` 的短期内部令牌。
- Base URL 必须经过协议、DNS、内网/回环和重定向检查；本机 HTTP 只允许显式开发配置。
- 每次真实 provider 请求只允许一次受控 DNS 解析，连接主体必须固定使用已验证地址，同时保留原始 Host、SNI 和 TLS 证书校验；禁止重定向和连接阶段二次解析，防止 DNS 重绑定。
- 切换 provider、地址、模型或密钥后必须重新测试。
- 连接测试成功与长期凭据保存是两个独立阶段；任一失败都不能标记为可运行。

## 4. 店铺客服内容 v2

店铺内容按 `用户 + 店铺` 隔离，至少包含：

| 字段 | 页面表达 |
| --- | --- |
| `store_content` | 店铺与客服说明，多行自然语言 |
| `persona.preset` | 专业、亲切、猫娘或自定义 |
| `persona.name` | 客服角色名称 |
| `persona.tone` | 专业、自然、活泼或克制 |
| `persona.buyer_address` | 对买家的称呼 |
| `persona.reply_length` | 简短、标准或详细 |
| `persona.emoji_level` | 不使用、少量或适量 |
| `forbidden_claims` | 不要承诺什么，自然语言 |
| `handoff_rules` | 什么时候转人工，自然语言 |
| `enabled` | 该店铺内容是否允许用于 AI 回复 |

规则：

- 新店铺可显示安全的人格初始选择，但没有实质 `store_content` 时不能显示为已生效或开启 AI。
- 不再提供 AI 故障固定 `fallback_reply`。超时、限流、空回复、预算不足或配置损坏时，本次安全不回复并等待人工。
- 人格只控制表达，不能覆盖实时事实、安全规则或履约约束。
- 保存使用 revision/CAS 和原子替换，迟到请求不能覆盖新版本。
- 模板只保存上述非敏感店铺内容，不包含连接凭据、商品内容、订单或买家消息。

## 5. 商品客服内容 v2

商品内容按 `用户 + 店铺 + item_id` 隔离。

### 5.1 实时事实

系统从当前店铺已验证商品快照读取并只读展示：

- 标题和描述；
- 当前价格或价格区间；
- 当前库存；
- SKU 与规格；
- 上下架或可用状态。

实时价格、库存、SKU 和状态优先于店主补充内容。买家自行描述的商品 ID 或价格不能替代可信快照。

### 5.2 自然语言补充内容

店主可填写一段商品客服内容，例如：

- 商品定位、适用人群和差异；
- 规格与使用条件；
- 使用方式和注意事项；
- 交付说明，但不得授权实际发货；
- 售后范围和争议处理；
- 常见问题与真实答案；
- 需要转人工的场景。

规则：

- 保存即原子生效，不再要求“保存草稿后批准发布”。
- 空白、纯标点、空数组、空旧结构或模型说明文字不能保存为有效内容。
- 停用是独立确认动作，停用不删除历史版本。
- 价格、库存和上下架变化只更新实时事实，不让整份补充内容过期。
- 标题、描述或 SKU 身份发生实质变化时，补充内容标记为“需确认”并暂停使用；AI 仍可依据实时事实和店铺内容回答有限问题。
- 旧 v1 非空字段可以合成为自然语言兼容内容并标记“由旧配置导入，建议确认”；全空旧对象不得继续算作已发布。

## 6. 统一回复引擎

### 6.1 输入

统一引擎接收：

- 当前买家消息；
- 最近有界历史，保留真实 `user/assistant` 角色；
- 当前可信 `item_id`；
- worker 刚读取的实时商品事实；
- 当前会话近期 AI 回复，用于去重。

控制面根据内部令牌作用域加载当前店铺连接、店铺内容和商品内容。浏览器或 worker 不能自行声明其他店铺的配置。

### 6.2 分层消息

最终模型消息按用途分层：

1. 系统安全与回答要求。
2. 店铺自然语言内容和表达方式。
3. 当前商品实时事实。
4. 当前商品可用的补充内容。
5. 最近对话历史。
6. 最后一条 `user` 消息必须是当前问题。

所有店铺、商品、历史和买家内容都作为不可信资料引用，不能覆盖系统指令。

### 6.3 有界压缩

- 当前问题、实时价格/库存/SKU/状态、商品核心内容和最近对话优先保留。
- 超长时逐字段、逐段压缩，禁止直接把整份商品内容设为空。
- 单条消息和总字符数必须满足 provider adapter 上限。
- 不向模型发送凭据、内部令牌、订单正文、库存备份、日志或跨账号资料。

### 6.4 内部决策

内部接口返回受限结果：

```json
{
  "decision": "reply",
  "reply": "可发送的客服文本",
  "reason_code": "ok",
  "sources": ["store_content", "realtime_product", "product_content", "conversation"],
  "knowledge_status": "ready",
  "config_revision": "本次生成绑定的精确配置版本"
}
```

`decision` 只允许：

- `reply`：通过全部检查的客服文本；
- `handoff`：需要人工处理；
- `no_reply`：当前没有可信回复。

该 JSON 是内部协议，不能在普通页面中作为编辑内容展示。

### 6.5 输出安全检查

模型返回后统一检查：

- 非空和长度；
- 不能是代码块、配置 JSON 或模型说明；
- 不包含内部魔法标记；
- 不引导站外联系方式；
- 不作未经证明的付款、发货、退款、永久可用等承诺；
- 不违反当前店铺 `forbidden_claims`；
- 不与同会话近期 AI 回复相同或高度相似。

首次重复可带“回答当前新问题、不要复述上一条”有界重试一次；仍重复则 `no_reply`。

## 7. worker 处理顺序

```text
收到可信闲鱼消息
  → 校验账号、会话、消息时间、系统消息和入站幂等
  → 确定 chat_id、buyer_id、可信 item_id
  → 检查总开关、人工接管、营业时间和冷静期
  → 匹配商品固定规则
  → 匹配店铺固定规则
  → rules_ai 未命中时调用内部统一回复接口
  → 持久化 decision、回复来源和精确 config_revision
  → 检查回复安全、近期重复和规则/设置指纹
  → 每次实际发送前再次复核自动化状态、AI enabled、精确 config_revision、人工接管和幂等草稿
  → 仅发送全部复核通过的文本
```

补充规则：

- `first_reply` 和规则页 `fallback_reply` 只属于纯 `rules` 模式。
- `rules_ai` 不发送 AI 故障固定兜底。
- 固定规则文件损坏时暂停全部自动回复，不能清空规则后继续 AI。
- AI 配置损坏时固定规则仍可工作，未命中项安全不回复。
- AI 草稿必须带来源和精确 `config_revision`；缺少任一项的旧草稿不得发送。
- 固定规则草稿必须绑定规则文件与自动化设置的稳定指纹；生成后、延迟后、重试和重启恢复时发现版本变化都要取消。
- 同一入站消息仅在绑定的状态与版本仍有效时复用稳定草稿；配置变化后不得重放旧正文。
- readiness 或模型同步调用超时后，其后台任务仍占用并发槽直到真正退出，不能释放锁后与下一次请求重叠。

## 8. 工作台

“智能客服”下包含：

1. 会话工作台。
2. AI 客服设置。
3. 固定规则与全局风控。

### 8.1 AI 客服设置

页面包括：

- 当前店铺和 AI 状态；
- 五格式模型连接、测试、保存和删除密钥；
- 店铺与客服说明；
- 简单人格与语气选择；
- 禁止承诺和转人工条件；
- 商品列表、实时事实和商品客服内容；
- AI 帮我整理、预览、采用、保存、停用；
- 连续对话沙盘测试。

页面不得出现：

- 可编辑 JSON；
- `aiPersonaJson`、`aiKnowledgeJson` 等内部字段名；
- “结构化知识库”“批准发布”“配置文件路径”；
- 完整系统提示词、密钥、内部令牌或原始上游错误。

### 8.2 整理预览

- 整理请求不会修改编辑器、保存或激活内容。
- 页面先显示自然语言建议。
- 代码块 JSON、空文本、模型自我说明或安全错误不可采用。
- 店主点击采用并二次确认后，只填入编辑区；保存仍是独立动作。

### 8.3 沙盘

沙盘必须显示：

- 实际回复或安全决策；
- 使用了哪些资料：实时事实、店铺内容、商品补充和会话；
- 商品内容状态；
- 安全状态和有界耗时摘要。

沙盘不得向闲鱼发送消息，也不得展示 raw prompt 或用“已命中知识”冒充真实回答。

## 9. API 边界

公开接口继续使用当前登录会话和经服务端验证的 `X-Shop-Account`：

- `/api/bot/ai/status`
- `/api/bot/ai/connection`
- `/api/bot/ai/connection/test`
- `/api/bot/ai/config`
- `/api/bot/ai/templates`
- `/api/bot/ai/products`
- `/api/bot/ai/products/{item_id}/knowledge`
- `/api/bot/ai/products/{item_id}/disable`
- `/api/bot/ai/products/{item_id}/extract`
- `/api/bot/ai/preview`

旧 `/publish` 仅保留 v1 客户端兼容，必须执行相同的实质内容和商品身份校验；新前端不再调用。公开响应不得返回旧 `draft`、`published`、`history` 或发布修订模型字段，商品整理只返回自然语言预览并明确不保存。

真实 worker 使用 loopback `/internal/v1/ai/reply` 生成受限决策，并在每次实际发送前调用 `/internal/v1/ai/ready` 复核精确 `config_revision`。这两个入口必须同时校验：

- 请求来自本机边界；
- Bearer 短期令牌有效；
- `X-Shop-Account` 与令牌账号一致；
- 用户与店铺可用；
- 模型连接已验证；
- 店铺内容有效且已启用；
- `/internal/v1/ai/ready` 收到的 expected revision 格式有效并与当前精确版本一致。

接口只返回受限决策、精确配置版本和安全摘要，不返回提示词、凭据或上游原文。

## 10. 状态与错误

公开状态至少区分：

- `unconfigured`：尚未填写有效内容；
- `ready`：连接、店铺内容和运行条件有效；
- `disabled`：店主主动停用；
- `needs_confirmation`：商品身份变化，补充内容需确认；
- `invalid`：配置损坏或不符合 schema；
- `model_unavailable`、`rate_limited`、`budget_exhausted`；
- `handoff`、`duplicate_reply`、`unsafe_reply`。

配置缺失与配置损坏必须区分。损坏不能静默当作空内容继续生成。

账号级 `reply_rules.json` 与 `automation_settings.json` 只允许在明确注册或新建店铺时播种安全初始文件。既有账号缺失、损坏或权限不安全时，普通状态查询应返回自动化关闭和 `automation_available=false`，Worker 手工启动、登录后自动启动和 API 重启恢复都必须 fail-closed；补齐有效私有文件后才可恢复。`rules_ai` 还要求当前账号 AI 配置有效。

## 11. 兼容与迁移

- v1 店铺配置读取时提取非空 `common_knowledge`、人格说明、禁止承诺和转人工规则，映射为 v2 自然语言内容。
- 默认猫娘人格、默认兜底和所有知识字段为空的 v1 对象不得自动启用 AI。
- v1 商品非空字段按分组拼为自然语言兼容内容；未知字段不进入模型。
- 迁移读取不能覆盖原文件或自动发布新版本；下一次店主保存后写入 v2。
- 账号、店铺、商品目录和历史版本继续保持隔离。

## 12. 验收标准

1. 页面没有 JSON 编辑器、结构化知识库或批准发布操作。
2. 新店铺没有实质内容时不能显示为 AI 已生效或开启 `rules_ai`。
3. 空白、纯标点和全空 v1 商品内容不能保存生效或通过兼容发布。
4. 固定规则命中时模型调用次数为零，原样回复。
5. `rules_ai` 首次真实问题进入统一引擎，不被欢迎语覆盖。
6. 沙盘和 worker 对同一输入使用相同资料层级、内容状态和安全检查。
7. 无商品补充时可依据实时事实有限回答；配置损坏时停止 AI。
8. 超时、限流、空回复、预算耗尽和格式错误不会连续发送相同固定兜底。
9. 同会话近期重复或高度相似回复会被重试一次或阻止。
10. AI 输出不能触发试用码、教程、发货或订单状态变化。
11. 实时价格、库存和状态覆盖冲突旧内容；商品身份变化令补充内容需确认。
12. 双用户、双店铺、同 `item_id/chat_id` 测试均无串用；迟到响应不污染新作用域。
13. 长期密钥只在控制面加密保存，worker 仅持账号短期令牌。
14. 桌面与 390px 可以完成连接、填写、整理预览、保存、停用和连续问答测试。
15. 专项 AI/API/worker/UI 合同、完整 `npm test` 和 `git diff --check` 通过。
16. 本机开发实例刷新与真实第三方模型、真实闲鱼和生产部署必须分别报告，不得混写。
17. AI 回复每次实际发送前都复核自动化状态、AI enabled 和精确 `config_revision`；配置变化后旧回复被取消。
18. 固定规则草稿在延迟、重试和重启恢复时都校验规则/设置指纹，不能发送旧正文。
19. 既有账号控制文件缺失或损坏时状态查询安全降级且所有自动启动/恢复 fail-closed；只有显式新账号初始化可播种。
20. provider 连接使用一次受控 DNS 解析并固定连接地址，连接阶段不发生二次解析。
