# 闲鱼自动客服与发货 Worker

`worker/` 是单店铺消息处理与自动发货进程，在 SaaS 控制面的统一监管下协同运行。每个店铺账号分配独立的运行环境、配置与会话边界；Worker 监听闲鱼平台事件，优先执行关键词规则，必要时调用控制面 AI 客服，并在核验官方订单后执行发货。

> **架构定位说明**：`worker/` 属于由系统控制面按店铺统一调度的内部工作进程，不是单独发行的独立客户端，也不支持作为独立服务单独部署。整个系统统一通过根目录 Docker Compose 或 Ubuntu 原生管理器进行部署，由控制面统一管理 Worker 的多进程生命周期。

## 运行模式与协同机制

Worker 受 SaaS 控制面统一管理，由控制面在启动时指定运行模式（`AUTOMATION_MODE`）：

- `rules`：纯规则模式，只执行预设关键词回复与发货，不初始化 AI 客户端。支持固定资料（`material`，仅支持单件）、网盘资源（`pan`）与卡密库存（`redeem`，消耗库存）的发货；
- `rules_ai`：规则与 AI 结合模式，优先匹配关键词规则；规则未命中且满足触发条件时，向控制面请求由大模型生成客服回复。

账号配置中的 `rules_enabled` 与 `ai_enabled` 分别控制两类回复，运行中可热更新；旧版只有 `enabled` 的配置由两类开关继承原值。回复开关与订单发货分开：关闭客服回复不停止 Worker，有有效发货配置时仍监听并处理订单。

AI 服务端由控制面统一组装上下文，大模型仅负责生成客服建议文本或转人工决策。大模型无权修改订单状态，无法跳过订单核验直接发货，也无法跨店铺读取其他账号数据。

## 消息处理流程

1. **会话归属与幂等处理**：收到平台消息后，根据当前店铺商品快照或已核验的商品归属检查会话，再处理消息去重、人工接管及免打扰状态。本账号作为买家的聊天不触发客服；尚未确认归属的会话不自动回复。平台买家昵称和待人工标记按会话保存；过期买家消息只入库供人工查看；
2. **人工接管隔离**：人工在工作台介入后仅抑制当前会话的自动回复链，不影响其他买家会话，亦不暂停店铺已核验订单的发货流程；
3. **规则优先匹配**：规则客服开启时，优先匹配当前商品的专属关键词规则，未命中时匹配店铺通用规则；
4. **AI 回复**：在 `rules_ai` 模式且 AI 开关开启时，若规则未命中或规则已关闭，向控制面请求生成回复。通过内容过滤后才发送；模型临时限流、超时和服务不可用时进行有界重试，失败不套用规则默认话术。较长回复按句子拆分为有限条消息，链接保持完整；
5. **人工回复队列**：操作人员在工作台提交的回复进入持久 Outbox，支持最多 8 张图片与文字排队发送，逐段确认平台协议 ACK，失败仅重试未送达部分；
6. **统一发送节流**：规则、AI、人工和发货消息共用当前 Worker 的串行发送槽，默认前次发送结束后至少等待 3 秒。连接等待、发送前复核及失败重试均在槽内处理，避免重连后集中连发。`OUTBOUND_MIN_INTERVAL` 控制间隔，`OUTBOUND_JITTER` 控制额外随机等待；受管环境默认分别为 3 和 0 秒。客服通用延迟、营业时间、人工接管及配置版本检查仍按各自规则生效。

## 自动发货核验机制

自动发货属于独立履约流程，不受规则/AI 回复开关、人工接管状态或客服营业时段限制。系统在接收到订单付款事件后，执行以下流程：

1. 调用平台官方 `HeadInfo` 与 `OrderDetail` 双接口核验订单；
2. 核对买家 ID、卖家身份、商品 ID 与订单状态，确认订单处于待发货状态（`status == 2`）；
3. 固定文字资料仅支持单件发货；网盘资料直接下发共享链接与提取码；卡密类型在本地库存事务中锁定并扣减库存；
4. 核验一致且库存处理成功后，通过私信向买家下发发货内容；
5. 任何环节出现异常时，终止本次自动发货，根据异常类型进入重试、待人工处理等对应状态。

### 待发货订单补扫

Worker 连接后定期读取平台待发货订单列表，补充发现停机或断线期间遗漏的付款事件。默认配置如下：

| 配置 | 默认值 | 含义 |
| --- | --- | --- |
| `PENDING_ORDER_SCAN_INTERVAL` | 300 秒 | 两轮正常扫描间隔，另加少量随机等待 |
| `PENDING_ORDER_SCAN_PAGES` | 1 页 | 单轮最多查询页数 |
| `PENDING_ORDER_SCAN_ROWS` | 30 条 | 每页订单数量 |

每笔订单先检查发货配置与退款状态，再核验订单详情中的买家、卖家、商品和待发货状态。没有可信历史聊天绑定时，通过平台创建会话并使用响应中的真实会话 ID；失败则留待后续扫描，不猜测会话 ID。

补扫复用实时付款路径的订单标识、库存预留、订单锁与发送前复核。已发货、待人工处理、已取消或已过期订单不会重复处理。每个 Worker 同时只执行一轮扫描，同轮重复订单去重；达到分页上限记录提示。平台风控与鉴权异常采用较长退避，认证不可用时停止扫描。

### 进程恢复

控制面通过持久的运行意图与 `auto_resume` 管理恢复。服务重启后恢复应运行的店铺；用户手动停止后保持停止，首次升级也保留旧版明确停止的记录。显式启动或重新扫码可重新启用恢复。关闭回复开关不等于停止进程，监控会区分自动回复、仅自动发货和其他运行状态。

接管或清理遗留进程前校验进程身份、启动时间与 PID/TID 归属，避免容器重启后的 PID 复用误伤 API 或任务消费者。

## 平台运行与防护状态说明

在与平台接口交互过程中，系统维护以下防护状态与时间窗口：

- **Worker 运行状态**：
  - `risk_control`：接口请求受限且保持保护状态，暂停当前操作并避免无节制重试；
  - `verification_required`：平台要求明确的安全验证，记录待办并提示人工介入；
- **控制面状态与防护窗口**：
  - `sync_cooldown`：店铺同步冷却，默认 60 秒，限制对闲鱼接口的主动查询频次；
  - `risk_cooldown`：接口遇风控后的 600 秒本地保护熔断，属于本地防冲撞限频保护，不代表平台实际解封时间，避免与常规同步冷却混为同一状态；
- **扫码确认有效期与连接租约**：扫码确认后会话有效期默认 90 秒。用户主动扫码或更换登录态不继承普通商品同步冷却，仍受并发操作租约和风险保护约束；短暂同步占用允许有限重试，平台风险冷却不自动连续重试。系统依据剩余有效期决定复用现有会话或重新扫码，新 Cookie 验证通过后才替换旧连接。

## 部署与运行架构

Worker 统一由控制面调度，不作为独立服务对外分发或单独部署：
- **整站统一部署**：系统整体通过根目录 `Dockerfile`（Docker Compose，推荐）或 Ubuntu 原生安装器（systemd 引导管理器）部署；控制面统一调度各店铺 Worker 的生命周期、配置与资源配额；
- **历史单 Worker 模板清理**：早期仓库中的 `worker/Dockerfile`、`worker/docker-compose.yml`、`worker/.dockerignore` 与 `worker/systemd/xianyu-autoagent.service` 重复部署模板已清理移除，避免误导读者将其当成第三种独立客户端；
- **内核机制依赖**：Worker 的多进程调度与资源限制依赖 Linux 内核接口（`fcntl` 文件锁、`/proc` 资源统计、`pidfd` 进程控制、`setsid` 会话隔离与 `RLIMIT_AS` 地址空间限额）；
- **平台支持**：Linux 环境原生支持；Windows 宿主机通过 Docker Desktop 搭配 WSL2 的 Linux 容器环境运行完整系统，不支持 Windows 原生直接运行全部服务。

## 本地调试与测试

Linux 环境下独立调试 Worker 进程（需自行在本地准备测试运行配置；日常生产与多店铺运行统一由控制面受管启动）：

```bash
./scripts/bootstrap-dev.sh
./scripts/dev-worker.sh
```

运行离线单元测试：

```bash
npm run test:worker
```

完整的代码风格、测试套件与契约检查：

```bash
npm test
npm run test:repository
npm run test:syntax
```
