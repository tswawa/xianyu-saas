# 项目 Memory 操作补充

通用流程见 `~/.codex/memory/MEMORY_OPERATIONS.md`。本文只规定 DeepWhale 闲鱼客服项目的文件边界、事实来源和复核方式。

## 文件分工

- `handoff/MEMORY.md`：项目稳定事实、产品决策、当前发布状态和验证入口；这是项目 memory 的唯一主索引。
- `handoff/AGENTS.md`：工作前检查、安全边界、架构边界和交付规则；这是项目指令，不是事实日志。
- `README.md`、`docs/`：详细搭建、部署和产品说明；memory 只引用结论，不复制整篇流程。
- `~/.codex/memory/daily/YYYY-MM-DD.md`：本机当天工作记录，不提交生产凭据或用户数据。
- `~/.codex/memory/reports/YYYY-MM-DD.md`：当天整理结果，供会话交接快速查看。

## 项目优先级

### P0：安全和真实性

1. 任何真实 Cookie、Token、Key、验证码、库存、订单/买家正文、数据库、日志和生产备份都不进 Git 或 memory。
2. 未完成真实扫码、验证码、安全认证、商品同步或履约验收时，必须标记 `unverified`。
3. 生产部署由维护者按精确 commit 串行完成；开发机不直接写生产目录。

### P1：架构与边界

把跨模块且会影响后续实现的架构事实写入 `handoff/MEMORY.md`，例如前端、backend、worker 的职责和内部接口边界。改动前后以源码、测试和用户明确决策复核。

### P2：产品决策和发布状态

会员权限、登录方式、履约核验和当前发布编号都可能变化。每次发布、产品决策或用户撤销决定时更新日期和状态；旧版本移到 `P4` 或归档，不保留两条互相矛盾的“当前”结论。

### P3：验证入口

只记录仓库已有且可复现的命令：`npm test`、`npm run test:auth`、`npm run test:update`、`npm run test:p0`、`npm run test:api`、`npm run test:worker`、`npm run test:ui`、`npm run test:deploy`、`npm run test:repository`。命令通过只证明对应合同通过，不代表真实账号或生产验收完成。

## 任务结束检查

1. `git status --short`，确认没有覆盖用户改动。
2. 根据风险运行必要测试、`git diff --check`，如无法运行说明原因。
3. 更新 `handoff/MEMORY.md` 的稳定结论和状态日期；一次性过程只写 daily log。
4. 在全局 report 中写新增、修正、验证和待办，并在回复中简要告知用户。

## 错误改进记录

用户指出错误后，项目 memory 只保留能跨任务复用的防错规则，例如“真实履约必须核验订单证明”；具体失败命令、临时环境问题和一次性修复放 daily log。每条规则必须有对应验证入口，避免只写口号。

## README 产品文档交付检查

- 先按真实 UI 结构确认产品入口，再写叙事；区分日常主域和侧栏辅助入口，不把页面数量或内部模块写成用户入口。
- 先描述店主会遇到的具体问题，再解释隔离、持久化、人工接管、AI 边界和履约核验等设计取舍；避免营销套话、无法证明的承诺和刻意对仗句式。
- 将验证证据分为离线合同、本机开发自检和真实环境验收三层；`npm test`、仓库合同和 `git diff --check` 只能证明前两层，不能代替真实平台或生产发布。
- README 截图只允许使用脱敏测试夹具，提交前检查图片尺寸、颜色模式、元数据和来源；不得包含账号、订单、买家、库存或凭据。
- 文档和截图改动不自动触发提交、推送或生产发布；除非用户另行明确授权，保留工作区改动并在交付中列出待办。

## 浅克隆或部分克隆的安全发布兜底

当 `git push` 与 `git push --no-thin` 都被远端 `index-pack` 拒绝时，先检查 `git rev-parse --is-shallow-repository`、`.git/shallow` 和浅边界提交的真实父引用。若浅边界父提交缺失且原历史源不可用，不得继续重复直推，也不得 force 或伪造原提交 ID。

在用户明确允许创建发布快照提交时，使用以下隔离流程：

1. 确认当前 `HEAD` 树对象完整可读，导出 `git archive HEAD`；运行时秘密和被忽略文件不得进入快照。
2. 在 `/tmp` 新建完整仓库，只读取目标远端当前 `main`，并以该提交作为新发布提交的父提交。
3. 导入快照、暂存后用 `git write-tree`、路径清单和秘密模式扫描核验内容；若源历史存在“已跟踪但现被忽略”的文件，必须显式审核差异，不能假定树完全相同。
4. 用 `git merge-base --is-ancestor`、父提交检查和 `git fsck` 确认远端历史保留且新提交可快进；推送前再次只读确认远端 tip 未变化。
5. 只做普通非强制推送；推送后独立重新 clone，并用树哈希与逐字节 diff 验证远端内容和历史。
6. 清理临时仓库，不改写源工作仓库，不修改 Git 配置。

GitHub 私有仓库认证在 Linux 使用 GCM `cache` 存储时可能随缓存进程退出或过期而失效；不要为每条命令分别触发浏览器授权。需要远端批量操作时，应先显式完成一次授权，再在同一有界流程中完成操作与终检；凭据内容不得进入命令输出、日志或 memory。

使用 GitHub Git Database API 时，读取单个引用使用 `/git/ref/...`，更新引用使用 `/git/refs/...`。更新必须传 `force:false`，写入前后分别读取分支指针，并核对新提交只有一个预期父提交；接口路径错误返回 404 时不得假定仓库不存在或分支已改变。
